# Entity lint rules

Generated by `er-entity lint --docs` from the `er-entity-lint` registry — do not hand-edit.
`er-entity verify` fails if this file and the registry disagree.

These are the **entity** conventions, checked against `entities/*/entity.yaml`. The
**statement** diagnostics (`E0xx`), which need a query planner, are a separate family
in `er-sql-check`.

| Code | Severity | Invariant |
|---|---|---|
| [V1](#v1) | error | an entity declares a NOT NULL `id` column, either varchar or bigint+serial |
| [V2](#v2) | error | the primary key is exactly `[id]` |
| [V3](#v3) | error | `id` is the first declared column |
| [V4](#v4) | error | an entity declares `created_at` and `updated_at` as NOT NULL timestamps |
| [V5](#v5) | error | a Postgres entity's timestamps carry a default and are `volatile: true` |
| [V6](#v6) | error | a lake entity's timestamps are not `volatile` |
| [V7](#v7) | error | a foreign-key column is named `<singular relation>_id`, optionally role-prefixed |
| [V8](#v8) | error | a foreign key references `id`, never another column |
| [V9](#v9) | error | every `references` target is a declared Postgres relation and a real column of it |
| [V10](#v10) | error | a declared `natural_key` names real columns, without repeats, and never `id`/`created_at`/`updated_at` |
| [V11](#v11) | error | a DuckLake entity declares no default, reference, `accepted_values`, `serial` or index |
| [V12](#v12) | error | an entity with an arrow or json `wire` also generates for `rust` |
| [V13](#v13) | error | `history: true` appears only on an entity with a `postgres` store |
| [V14](#v14) | error | no declared relation collides with a `history: true` entity's `<relation>_history` companion |
| [V15](#v15) | warning | a control-plane entity with an `org_id` column declares a non-partial index leading with `org_id` |
| [V16](#v16) | error | an entity generating for `typescript` declares an arrow or json `wire` |

## V1

an entity declares a NOT NULL `id` column, either varchar or bigint+serial

`id` is the one way any row in the system is addressed, so it cannot be absent or null. Two shapes are allowed and no more: varchar, holding a UUIDv7 the application mints or a sha256 text the SQL mints, and bigint with `serial: true` for a database-minted ledger such as audit_log or ddl_log. The history trigger keys row images by `id`, so an entity without one cannot carry history either.

Severity: **error**

Conforming:

```yaml
columns:
  - name: id
    type: varchar
    nullable: false
    description: "The row's unique id (UUIDv7, minted at creation)."
```

Violating:

```yaml
columns:
  - name: record_key
    type: varchar
    nullable: false
    description: "No id column at all."
```

## V2

the primary key is exactly `[id]`

Natural identity — what makes two rows the same thing — belongs in `natural_key`, where MERGE statements read it (E015) and where it can change without rewriting every foreign key that points here. Keeping the primary key uniformly `[id]` is what lets the generator emit one row-image trigger, one by-id read and one FK shape for every entity in the tree.

Severity: **error**

Conforming:

```yaml
key: [id]
natural_key: [record_key]
```

Violating:

```yaml
key: [record_key]
```

## V3

`id` is the first declared column

Column order is declaration order everywhere downstream — the generated struct, the DDL, the Arrow schema, the TypeScript interface. Pinning `id` first gives every one of those a uniform shape, so a reader who knows one entity can read the next without re-learning where identity lives.

Severity: **error**

Conforming:

```yaml
columns:
  - name: id
    type: varchar
    nullable: false
    description: "…"
  - name: record_key
    type: varchar
    description: "…"
```

Violating:

```yaml
columns:
  - name: record_key
    type: varchar
    description: "…"
  - name: id
    type: varchar
    nullable: false
    description: "…"
```

## V4

an entity declares `created_at` and `updated_at` as NOT NULL timestamps

Every row can answer when it appeared and when it last changed, with no per-entity exceptions to remember. Universality is the point: it lets the analyser demand that mutations advance `updated_at` (E014) and lets `created_at` be treated as immutable (E005) without consulting the entity first. Nullable would reintroduce exactly the per-row doubt the rule removes.

Severity: **error**

Conforming:

```yaml
  - name: created_at
    type: timestamp
    nullable: false
    description: "…"
  - name: updated_at
    type: timestamp
    nullable: false
    description: "…"
```

Violating:

```yaml
  - name: created_at
    type: timestamp
    description: "Nullable, and no updated_at at all."
```

## V5

a Postgres entity's timestamps carry a default and are `volatile: true`

Control-plane rows are written by the server as things happen, so their timestamps are wall-clock: `default: "now()"` means an INSERT need not pass one, and `volatile: true` excludes them from determinism comparisons, which would otherwise fail purely because time passed between two runs. This is the mirror of V6 — the store decides which of the two a timestamp is.

Severity: **error**

Conforming:

```yaml
  - name: created_at
    type: timestamp
    nullable: false
    default: "now()"
    volatile: true
    description: "…"
```

Violating:

```yaml
  - name: created_at
    type: timestamp
    nullable: false
    description: "No default, not volatile — but the entity is on postgres."
```

## V6

a lake entity's timestamps are not `volatile`

Lake rows are written by a run, from the run's own logical clock, and are part of the determinism contract: the same inputs must reproduce the same timestamps, which is exactly what a determinism comparison checks. Marking one volatile would exempt it from that comparison and quietly surrender the guarantee. The mirror of V5. (A genuinely wall-clock lake column — an assembly stamp — is a separate column, free to be volatile.)

Severity: **error**

Conforming:

```yaml
  - name: created_at
    type: timestamp
    nullable: false
    description: "Creation stamp (the run's logical timestamp)."
```

Violating:

```yaml
  - name: created_at
    type: timestamp
    nullable: false
    volatile: true
    description: "…"
```

## V7

a foreign-key column is named `<singular relation>_id`, optionally role-prefixed

The column name alone should say where it points, so a reader never has to open the referenced entity to find out. `orgs` is referenced by `org_id`; a role-prefixed form (`parent_org_id`) is allowed for the case where one entity references the same relation twice and the names have to differ. The singular is mechanical — see `singular()` in er-entity-spec.

Severity: **error**

Conforming:

```yaml
  - name: org_id
    type: varchar
    nullable: false
    references: { relation: orgs, column: id }
    description: "…"
```

Violating:

```yaml
  - name: tenant
    type: varchar
    nullable: false
    references: { relation: orgs, column: id }
    description: "…"
```

## V8

a foreign key references `id`, never another column

V2 makes `id` the primary key of every entity, so it is the only column guaranteed unique and stable enough to be pointed at. Referencing a natural-key column instead would couple this entity to a value the other entity is free to redefine.

Severity: **error**

Conforming:

```yaml
    references: { relation: orgs, column: id }
```

Violating:

```yaml
    references: { relation: orgs, column: name }
```

## V9

every `references` target is a declared Postgres relation and a real column of it

References used to be taken on faith: the generator emitted the FK clause and a typo surfaced as a Postgres error at schema-apply time, in a different process on a different day. Resolving the target against the catalog moves that failure to the moment the YAML is edited. This is a property of the whole tree, so a deliberately partial catalog (the differ's tests, a focused tool) can load without it and check later.

Severity: **error**

Conforming:

```yaml
# with entities/org declaring `relation: orgs` and an `id` column:
    references: { relation: orgs, column: id }
```

Violating:

```yaml
    references: { relation: parents, column: id }  # no such relation
```

## V10

a declared `natural_key` names real columns, without repeats, and never `id`/`created_at`/`updated_at`

`natural_key` answers what makes two rows the same thing, and the analyser holds MERGE statements to it (E015), so a typo here silently changes what a merge considers a match. The universal columns are excluded because they are row identity and bookkeeping, not natural identity — keying on `id` would make the merge a no-op and keying on a timestamp would make it nondeterministic. Nullable columns are allowed: a merge identity can be partial.

Severity: **error**

Conforming:

```yaml
natural_key: [org_id, source_name]
```

Violating:

```yaml
natural_key: [created_at]
```

## V11

a DuckLake entity declares no default, reference, `accepted_values`, `serial` or index

DuckLake enforces NOT NULL and nothing else — no defaults, no foreign keys, no CHECK constraints, no indexes. Declaring one would generate DDL the lake silently ignores, which is worse than an error: the YAML would promise a guarantee no layer actually provides, and a reader would be entitled to rely on it. Control-plane features belong on `stores: [postgres]` entities.

Severity: **error**

Conforming:

```yaml
generate:
  stores: [duckdb]
  languages: [rust]
columns:
  - name: status
    type: varchar
    nullable: false
    description: "…"
```

Violating:

```yaml
generate:
  stores: [duckdb]
  languages: [rust]
columns:
  - name: status
    type: varchar
    nullable: false
    default: "'active'"
    accepted_values: [active, closed]
    description: "…"
```

## V12

an entity with an arrow or json `wire` also generates for `rust`

A wire format is how this entity crosses a process boundary, and every such boundary in this system has Rust on at least one end — the engine writes the Arrow batch, the server serialises the JSON. Declaring a wire without Rust describes a shape nothing can read or produce.

Severity: **error**

Conforming:

```yaml
generate:
  stores: [duckdb]
  languages: [rust, typescript]
  wire: [arrow, json]
```

Violating:

```yaml
generate:
  stores: [duckdb]
  languages: [typescript]
  wire: [json]
```

## V13

`history: true` appears only on an entity with a `postgres` store

Row-image history is implemented by a Postgres AFTER trigger writing into a generated `<relation>_history` companion. The lake has no triggers — its history is DuckLake snapshots, which it keeps whether or not anything is declared. So `history: true` on a lake entity cannot be honoured, and asking for it suggests the author expected a companion table that will never exist.

Severity: **error**

Conforming:

```yaml
generate:
  stores: [postgres]
  languages: [rust]
  history: true
```

Violating:

```yaml
generate:
  stores: [duckdb]
  languages: [rust]
  history: true
```

## V14

no declared relation collides with a `history: true` entity's `<relation>_history` companion

`history: true` makes the generator emit a `<relation>_history` table and a trigger that writes row images into it. If some other entity already declares that relation, the two definitions of the same table fight: whichever DDL applies last wins, and the row images land in a shape nothing expects. Catching the name collision in the catalog is the only place it is still cheap.

Severity: **error**

Conforming:

```yaml
# orgs declares `history: true`, and nothing else declares `orgs_history`.
```

Violating:

```yaml
# orgs declares `history: true`, and some other entity declares
# `relation: orgs_history`.
```

## V15

a control-plane entity with an `org_id` column declares a non-partial index leading with `org_id`

`org_id` is how the control plane scopes a row to a tenant, so essentially every read of such a table filters on it. Postgres can only use an index for that filter if `org_id` is the index's leading column — a composite like `[org_id, state]` serves it, `[state, org_id]` does not — and only if the index is not partial, since a `where` predicate narrows it to rows the general lookup cannot assume. Without one, every tenant-scoped query is a sequential scan over every tenant's rows, which degrades as tenants are added rather than as any one tenant grows. Note that a unique partial index such as `jobs_one_active_per_org` enforces a real invariant and should stay: this rule asks for a plain index in addition, not instead.

Severity: **warning**

Conforming:

```yaml
columns:
  - name: org_id
    type: varchar
    nullable: false
    references: { relation: orgs, column: id }
    description: "…"
indexes:
  - name: staged_pending
    columns: [org_id, state]
```

Violating:

```yaml
columns:
  - name: org_id
    type: varchar
    nullable: false
    references: { relation: orgs, column: id }
    description: "…"
# …and either no indexes at all, or only partial ones:
indexes:
  - name: jobs_one_active_per_org
    columns: [org_id]
    unique: true
    where: "state IN ('running')"
```

## V16

an entity generating for `typescript` declares an arrow or json `wire`

The TypeScript binding emitter is gated on a wire: with none declared, `languages: [typescript]` emits nothing at all and no gate notices, so the YAML claims a frontend type that does not exist and the frontend hand-writes one instead — which is the drift the generated bindings were introduced to stop. This was found the honest way: a new entity declared `typescript`, no binding appeared, and `verify` was perfectly happy. V12 covers the other direction (a wire needs a Rust end); together they make the stores/languages/wire triple consistent.

Severity: **error**

Conforming:

```yaml
generate:
  stores: [postgres]
  languages: [rust, typescript]
  wire: [json]
```

Violating:

```yaml
generate:
  stores: [postgres]
  languages: [rust, typescript]
```
