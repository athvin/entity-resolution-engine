## BLOCKERS

### B1. The Compose substrate cannot start, and nothing it produces reaches CI
**SEVERITY:** BLOCKER
**SECTIONS:** S7 (all services), S9.1, S9.2, S3 (`lake/ducklake.py`, `dbt/profiles/profiles.yml`)
**THE HOLE:** Six independent defects in the substrate the doc calls "exactly what CI runs." `MINIO_ROOT_USER: er` is 2 chars — MinIO refuses to start (min 3/8), so `objectstore-init` never completes and `pipeline` blocks forever. `--abort-on-container-exit` tears the stack down the moment the one-shot init container exits, so the reported exit code is a teardown signal, not a test result. No service declares `volumes:`, so `artifacts/` never exists on the runner and both uploads are empty; `report.py --compare` then reads a file that cannot exist. The pipeline gets no S3 credentials, no `DATA_PATH`, and no lake alias, so no DuckLake write can succeed.
**THE FIX:** In S7: (a) `MINIO_ROOT_USER: erminio` / `MINIO_ROOT_PASSWORD: erminiopassword`, propagated to the `mc alias set` entrypoint; (b) add to `pipeline` and `benchmark`: `ER_S3_ACCESS_KEY_ID`, `ER_S3_SECRET_ACCESS_KEY`, `ER_S3_REGION=us-east-1`, `ER_S3_URL_STYLE=path`, `ER_S3_USE_SSL=false`, `ER_LAKE_DATA_PATH=s3://lake/er/`, `ER_LAKE_ALIAS=lake`, and `ER_CONFIG` on `benchmark` (currently missing); change `ER_S3_ENDPOINT` to `objectstore:9000` (host:port, no scheme); (c) `volumes: ["../artifacts:/app/artifacts"]` on both, plus `mkdir -p artifacts` in CI and `if-no-files-found: error` on both uploads; (d) top-level `name: er` plus `image: er-pipeline:ci` + `pull_policy: never` so Compose consumes the prebuilt image instead of rebuilding as `docker-pipeline`; (e) replace `up --abort-on-container-exit --exit-code-from pipeline` with `run --rm pipeline pytest tests/integration -q --junitxml=/app/artifacts/junit.xml --maxfail=3` in S7, S9.1 and S9.2, plus an `if: always()` `down -v --remove-orphans`. Add a literal statement block to S7 that `lake/ducklake.py` and the dbt profile both emit: `INSTALL/LOAD ducklake,postgres,httpfs; CREATE OR REPLACE SECRET er_s3 (TYPE s3, KEY_ID …, SECRET …, ENDPOINT 'objectstore:9000', URL_STYLE 'path', USE_SSL false, REGION 'us-east-1'); ATTACH IF NOT EXISTS 'ducklake:postgres:' || $ER_CATALOG_DSN AS lake (DATA_PATH '$ER_LAKE_DATA_PATH', METADATA_SCHEMA 'er_main');` — note explicitly that `postgresql://` URIs are accepted by the postgres extension and need no translation, and that `DATA_PATH` is written into the catalog on first attach and is immutable thereafter. Install `httpfs/postgres/ducklake` at Docker **build** time into `/opt/duckdb_extensions` with `autoinstall_known_extensions=false` at runtime.

### B2. DuckLake enforces only NOT NULL, but S5 declares a PRIMARY KEY and is called "the source of truth"
**SEVERITY:** BLOCKER
**SECTIONS:** S5, S3 (`lake/ddl.py`, `ingest/landing.py`), S4.1, S8.1
**THE HOLE:** `raw_records(... PRIMARY KEY (source_system, source_record_id, content_hash))` will not execute — DuckLake supports no PK/UNIQUE/FK/CHECK, no indexes, no sequences, no non-literal DEFAULTs, no ENUM. `ddl.py` therefore cannot be written as specified and M1 cannot exit. Downstream: S3 says `landing.py # raw_records upsert` while S4.1 says "Appends to `raw_records`" — with `content_hash` in the key those are different tables, and no other S5 table declares any key at all.
**THE FIX:** Delete the PRIMARY KEY clause and add to S5: "DuckLake enforces NOT NULL only. Every key below is a *logical* key, enforced by dbt `unique`/`unique_combination_of_columns` tests and by `MERGE INTO` on write; no sequences, no `DEFAULT now()`, no generated columns, no ENUM — all IDs are ULIDs minted in Python, all timestamps are supplied by the writer, and all `∈ {…}` domains are VARCHAR validated by `accepted_values` tests. `payload/details/evidence/metrics JSON` and `name_variants LIST` are supported and retained; fixed-size ARRAY is not." Then state a logical key for all fourteen tables (none currently has one). Resolve the append/upsert contradiction by picking append-only version history (see Decision 6) and restating S4.1 as an anti-join append on `(source_system, source_record_id, content_hash)`. Add T-KEY-1: insert a duplicate key directly and assert the dbt uniqueness test fails.

### B3. No Splink 4 API accepts a precomputed pair table, and `find_matches_to_new_records` cannot produce within-batch pairs
**SEVERITY:** BLOCKER
**SECTIONS:** S4.3 (`incremental.py` steps 1–2), S8.2 `incremental_batch`, S8.3 T-INC-1
**THE HOLE:** S4.3 computes candidate pairs in DuckDB and then says "score candidates via Splink two-frame `link` / `find_matches_to_new_records` pattern." Splink 4's entire inference surface is `deterministic_link` / `predict` / `find_matches_to_new_records` / `compare_two_records`; none takes a pair list, all regenerate pairs from blocking rules. So step 1's output has no consumer, step 2 names two incompatible mechanisms as one, and `find_matches_to_new_records` explicitly does not pair new records with each other — which is exactly the "2 form a new entity" case the committed `incremental_batch` fixture requires.
**THE FIX:** Replace S4.3's `incremental.py` bullet with two named Splink passes, unioned: (1) new-vs-corpus — `linker.inference.find_matches_to_new_records(records_or_tablename='batch_std', blocking_rules=<generated from S6 blocking:>, match_weight_threshold=log2(review_low/(1-review_low)))`; (2) new-vs-new — a second Linker over the batch alone with `link_type='dedupe_only'` calling `predict(threshold_match_probability=review_low)`, using the same frozen model JSON and the same registered TF tables. UNION, drop self-pairs, canonicalise to `rec_a_key < rec_b_key`, `DISTINCT`, persist. Add one sentence: "Splink regenerates its own candidate pairs; `int_blocking_keys` is therefore NOT an input to scoring — it is the source from which blocking rules are generated, the driver for the S4.5 touched-subgraph computation, and the `candidate_pair_count` benchmark metric." Add T-INC-3: score ~50 fixed pairs via the incremental and full paths at the same pinned `model_version` and assert bit-equal `match_probability` — if T-INC-3 fails, T-INC-1 cannot pass, and the failure is localised to scoring rather than clustering.

### B5. The split branch is uncodeable and unreachable: the affected **edge** set is undefined, splits have no trigger, and "majority fragment" has no tiebreak
**SEVERITY:** BLOCKER
**SECTIONS:** S4.5, S4.4, S8.2 `split_scenario`, S8.3 T-PERM-2, T-ASSERT-1
**THE HOLE:** S4.5 defines the affected **node** set (batch records + scored partners + their entity co-members) but never says which edges are loaded for those nodes; an implementer who loads only this run's scored pairs will spuriously fragment every touched entity, and one who loads all current edges is correct — both readings are consistent with the text. The affected set is seeded only by batch records, so a `never_match` asserted on two non-batch records touches nothing and `split_scenario` cannot execute in incremental mode at all, contradicting S4.4's "applied identically in incremental and full modes." And "majority fragment keeps ID (same deterministic tiebreaks)" is unimplementable: the cited tiebreaks (`oldest created_at`, `lexical ULID`) are entity-level properties every fragment shares, so a 2–2 split has no tiebreak — in direct contradiction of S4.5's own "All tiebreaks are total orders."
**THE FIX:** Three sentences in S4.5. (1) Edge set: "For every entity in the affected set, load ALL currently-active edges among its members (assertion-adjusted, ≥ `auto_merge`, at the run's `model_version`) — not merely this run's scored pairs — and recompute connected components over that full edge set. `match_scores` is cumulative and is never truncated per run." (2) Affected set: "affected = entities of batch records ∪ entities of records referenced by assertions created or retracted since the last successful run ∪ entities of records whose `content_hash` changed ∪ entities of deleted records; `er reconcile` reads the pending-assertion delta." (3) Split order: "fragments are ranked by `(member_count DESC, min member key (source_system, source_record_id) ASC)`; rank 1 retains the `entity_id`; a fragment of size 0 retires the entity; a record leaving all clusters becomes a singleton entity." Also pin label propagation: "label = min record_key over the closed neighbourhood, propagated to fixpoint; on failure to converge within `clustering.max_iterations` (S6, default 50) the stage fails — no snapshot committed, no events emitted, exit non-zero, unconverged component size logged." Add one line to S8.2 that `split_scenario`'s asserted edge must be a bridge. Unit-test the 2–2 split.

### M1. Record identity and pair orientation are undefined; assertions silently fail to match scores
**SEVERITY:** MAJOR
**SECTIONS:** S5 (`match_scores`, `assertions`, `review_queue`, `std_records`), S4.3, S4.4, S4.5
**THE HOLE:** S5 uses `rec_a`/`rec_b` as single columns with a comment claiming they are `(source_system, source_record_id)`. Splink additionally requires one scalar `unique_id` column, which no table provides. Most damagingly, no canonical pair orientation is stated: an assertion recorded as `(A,B)` will not match a score row stored as `(B,A)`, so S4.4's `never_match` removal is silently a no-op — which breaks T-ASSERT-1 and voids S4.4's stated purpose.
**THE FIX:** Add to S5 above the table list: "`record_key VARCHAR := source_system || ':' || source_record_id` is the canonical scalar record identity, materialized on `std_records` and `int_blocking_keys`, and is Splink's `unique_id_column_name`; `source_record_id` must not contain `':'` (dbt singular test)." Rename the pair columns to `rec_a_key`/`rec_b_key` across `match_scores`, `assertions`, `review_queue`, and add the invariant: "every pair is stored canonically as `rec_a_key < rec_b_key` lexically, canonicalised by one shared helper at write time; readers never need a two-sided join." Add `PRIMARY KEY`-equivalent logical keys and a dbt singular test for the invariant on all three tables, and cite it in S4.4 as the precondition making `never_match` correct and in S4.5 as part of the determinism total order.

### M2. `run_id` is referenced by four tables that have no referent; "exactly one snapshot per stage" is false; T-SNAP-1 and T-IDEM-1 are unwritable
**SEVERITY:** MAJOR
**SECTIONS:** S4 preamble, S5, S8.3 (T-SNAP-1, T-IDEM-1, T-INC-2), S10.3
**THE HOLE:** `run_id` is a column on `match_scores`, `entity_membership`, `entity_events` and `review_queue`, and no table defines a run — no mode, config, model version, status, timing, or snapshot boundary. S4's "commits exactly one DuckLake snapshot on success" is false for `er standardize` and `er assemble`: dbt commits per statement against DuckLake (its adapter documents the autocommit behaviour explicitly), so a 10-model run produces dozens of snapshots. T-SNAP-1 must time-travel to a "pre-incremental snapshot" whose id is never captured, and T-IDEM-1 asserts on snapshot counts that are unobservable.
**THE FIX:** Add to S5: `runs(run_id ULID, tenant, mode, started_at, ended_at, status, config_hash, model_version, std_version, survivorship_version, code_version, snapshot_start BIGINT, snapshot_end BIGINT)`, `run_stages(run_id, stage, seq, status, started_at, ended_at, rows_in, rows_out, snapshot_start, snapshot_end, error_class, error_detail)`, and `ingest_batches(ingest_batch_id, run_id, source_system, path, new_count, changed_count, unchanged_count, created_at)` — S4.1's manifest currently has no persistence target. Define `config_hash` as SHA-256 over the canonicalised Pydantic-validated config document (the term appears nowhere today). Replace the S4 sentence with: "Every stage is idempotent. A stage may commit many DuckLake snapshots — dbt-backed stages commit one per model — so each stage records the snapshot **range** it produced in `run_stages`; the range is the unit of time travel and rollback." Add a global `--run-id` to every S4 command (auto-minted ULID; `run-all` mints once and threads it). Rewrite T-SNAP-1 literally: read `run_stages.snapshot_end` for the pre-incremental `assemble`, then `SELECT * FROM lake.main.golden_records AT (VERSION => :snap)`. Rewrite T-IDEM-1 as a row-level assertion (manifest `new=0, changed=0`; zero new `entity_events`; row counts and content hashes unchanged) rather than snapshot counts, and add the clarifying sentence that a no-op run may legitimately produce empty snapshots. Add `er run-all --mode incremental` refuses to proceed when `(config_hash, model_version, std_version)` differ from the last successful run, with `--allow-escalate` to promote to full instead (T-CFG-1).

### M3. `entity_membership` is ambiguous between current-state and history
**SEVERITY:** MAJOR
**SECTIONS:** S5, S4.5, S4.6, S8.3 (T-INC-1, T-INC-2)
**THE HOLE:** `entity_membership(source_system, source_record_id, entity_id, assigned_at, run_id)` has no key, no `is_current`, no validity interval, and no statement of update-vs-append. `assigned_at` + `run_id` read as history; S4.5's "their partners' *current* entity co-members (one membership join)" and S5's `member_removed` event require current state. Under the history reading, `assigned_at` ties for every row a run writes and `run_id` is never stated to be ordered, so "current entity of record r" is genuinely undefined after a merge — and every downstream guarantee (T-INC-1's partition comparison, T-INC-2's touched set, mart assembly, the merge survivor rule) depends on it.
**THE FIX:** Add to S5: "`entity_membership` is CURRENT STATE — exactly one row per `(source_system, source_record_id)`, its logical key, maintained by `MERGE INTO`; `assigned_at` is the most recent (re)assignment. All membership history lives in `entity_events`." Add one line to S4.5: "on merge, loser members' rows are rewritten to the survivor in the same snapshot; `merged_into` exists only for external ID resolution, never for resolving current membership." Add dbt tests: exactly one row per record; every `entity_id` references an entity with `status='active'`. Make S3's promised "append + replay" checkable by stating the fold order `(occurred_at, seq)` and adding a unit test that replay reproduces `entity_membership`. Define T-INC-1's comparison concretely: group record_keys by entity_id into frozensets, compare sets of frozensets.

Rename S5's `std_records`/`blocking_keys` to `int_std_records`/`int_blocking_keys`. Add `golden_display` to S3 and S5. Resolve the mypy contradiction to `mypy --strict src/er` in S2, S8.1 and S9.1.

### M5. Reconcile's four branches assume each raw cluster maps to ≤1 prior entity; T-PERM-3's invariant is unstated; §6.2/§7.3 point at a document that does not exist
**SEVERITY:** MAJOR
**SECTIONS:** S4.5, S8.3 T-PERM-3, header, S8.4, S13
**THE HOLE:** Splink's `cluster_id` is the minimum `unique_id` in a cluster — a record-derived label that changes whenever membership changes — so reconcile must own a raw-cluster→entity mapping that S4.5 never defines. Its four branches are keyed on how many distinct `entity_id`s appear in a cluster, which tacitly assumes at most one prior partition per cluster; on full re-resolution a cluster can be simultaneously a merge of two entities *and* a split of a third, and no branch covers it — "multi-entity → merge" would silently merge two entities while abandoning the third's departed members with no split event. "Unchanged partitions" in T-PERM-3 is never defined. Meanwhile the spec delegates the algorithm to `entity-resolution-design-doc.md` §6.2 and §7.3, which are not in the repo.
**THE FIX:** Delete the "Companion document" header line and all `design doc §` references (add a CI lint on the string). Replace the four-branch list with the general mapping plus a named invariant: "**INV-PERM** — let `P_old` be the current membership partition and `P_new` the clustering output. For every group in `P_new` that is set-equal to a group in `P_old`, every member retains the existing `entity_id`, no ULID is minted, and no event is emitted. Otherwise: build the overlap matrix between `P_old` and `P_new`; each new group's claimant is the old entity with the largest overlap, tiebroken by min member key; old entities losing all members to a claimant are merged into it with a redirect; old entities left holding a strict subset are split per the fragment ordering in B5." This subsumes all four branches and covers merge-and-split-at-once. Restate T-PERM-3 as INV-PERM literally, plus "every entity whose partition changed has a corresponding merged or split event in this `run_id`", and state that both arms use the same `model_version`. Inline the §7.3 correction-pass policy (cadence, what it recomputes, the invariant it restores, `details.reason='correction_pass'` on its events, and that it never retrains).

### M6. Assertions have no id, no lifecycle, no precedence rule, no contradiction handling, and `never_match` is stated as a partition guarantee but implemented as edge deletion
**SEVERITY:** MAJOR
**SECTIONS:** S4.4, S4.5, S5 `assertions`, S8.2, S8.3 T-ASSERT-1, T-PERM-2
**THE HOLE:** `assertions(rec_a, rec_b, kind, created_by, created_at)` has no surrogate id, no active/retracted flag and no key, so a steward can never retract or supersede an assertion and a duplicate is indistinguishable from a re-assertion. S4.4 lists "never removed … always added" in that order, so an `always` row applied after a `never` removal resurrects the forbidden edge — precedence is never stated. Structurally, deleting edge `(a,b)` does not prevent `a–c–b` from re-linking them under connected components (Splink offers no must-not-link primitive), so `never_match` is a silent no-op whenever another path exists, and `always(a,b) ∧ always(b,c) ∧ never(a,c)` is satisfiable as edge operations but unsatisfiable as a partition — with no validation pass and no failure mode.
**THE FIX:** Redefine as `assertions(assertion_id ULID, rec_a_key, rec_b_key, kind, active BOOL, created_by, created_at, retracted_by, retracted_at, note)` with a dbt uniqueness test on `(rec_a_key, rec_b_key)` where `active` — which resolves the always/never conflict by construction. Add to S4.4: "never dominates always for the same pair; a conflicting insert is rejected at write time." Add a pre-clustering validation pass named **CONTRADICTION-1**: compute the connected components of the `always` edges and fail the run (exit non-zero, no snapshot) if any `never` pair falls inside one, naming the offending assertions. Then state the semantics explicitly: "`never_match` is an edge-level operation; if the endpoints remain connected by another path they will still share an entity, and this is reported as a `violated_assertion` row in `review_queue` rather than silently ignored." Restate T-ASSERT-1 as the invariant "no active `never` pair shares an `entity_id`, in either mode" and add a fixture case where the pair is connected through a third record. Wire the trigger (see B5's affected-set amendment) — without it S4.4's "applied identically in incremental and full modes" is false.

### M7. "Byte-identical reconciliation output" is impossible while minting ULIDs; the minting order is unspecified; `expected/` files cannot be authored
**SEVERITY:** MAJOR
**SECTIONS:** S4.5, S8.2, S8.3 (T-STD-1, T-PERM-1/2, T-GOLD-1, T-SNAP-1), S8.4
**THE HOLE:** S4.5 requires byte-identical output while every branch-1 case mints a timestamp+random ULID, and S8.4 tests the reconciler "as a pure function" with no injectable generator. Worse, the *order* in which new clusters are visited determines which cluster gets which ID, and S4.5 specifies total orders only for merge/split tiebreaks — DuckDB guarantees no scan order — so even with a seeded counter the cluster→ID map is not reproducible. Separately T-STD-1's "`std_records` byte-identical" is untestable: Parquet output is not reproducible and `std_records` carries `ingest_batch_id`. And S8.2 defines every scenario's expected set as a "membership crosswalk … as CSV," which by definition contains entity IDs.
**THE FIX:** Split the S4.5 requirement: "**D1** — the output partition and the cluster→`entity_id` assignment MAP are deterministic given identical inputs. **D2** — output is byte-identical *modulo minted identifiers*. New clusters are minted in ascending order of their minimum member key `(source_system, source_record_id)` — an explicit `ORDER BY` in the reconcile SQL, not an incidental scan order. `reconcile()` takes an `IdFactory` dependency (production: ULID; tests: monotonic counter)." Redefine T-STD-1 as a content hash over an explicit stable column list, and add a `VOLATILE_COLUMNS` list to S5 (`ingest_batch_id, ingested_at, assembled_at, scored_at, assigned_at, run_id, event_id`) excluded from every determinism comparison, defined once in `ddl.py`. Add S8.2.1 fixing the expected-file format: `expected/membership.csv (persona_id, source_system, source_record_id, entity_label)` where `entity_label` is symbolic (`E1`, `E2`) and never a ULID; `expected/golden.csv (entity_label, …)`; `expected/events.csv (entity_label, event_type, count)`. Specify `tests/helpers/compare.py` with three named functions — `assert_partition_equal` (ID-insensitive, T-INC-1), `assert_ids_stable` (ID-identical, T-PERM-*), `assert_golden_equal(…, float_tol=1e-9)` — plus the null token, excluded timestamps and sort key. Resolve the layout conflict: `expected/` lives inside each scenario dir; delete the top-level `fixtures/expected/` from S3.

### M8. The model artifact has no durable home, no version allocation rule, no active pointer, and training cannot be parameterised from config
**SEVERITY:** MAJOR
**SECTIONS:** S4.3, S5 `model_registry`, S6, S8.3, S12 M3
**THE HOLE:** `estimate_probability_two_random_records_match(deterministic_matching_rules, recall, …)` has two *required* arguments and `estimate_parameters_using_expectation_maximisation(blocking_rule, …)` requires a blocking rule per session (≥2 sessions are standard, since m is not estimated for blocked columns) — none of these exist anywhere in S6, so `er train` literally cannot be built from the config S4.3 says it reads. `estimate_u_using_random_sampling(max_pairs=1e6, seed=None)` is unseeded, so two trainings on the same corpus give different models. `models/model_v{N}.json` is a container-local path with no volume, no `models/` in S3, and no rule for allocating N; `model_registry` has no active flag, so "load frozen model" names no selection rule; and nothing says what a retrain does to existing `match_scores` rows, so clustering can mix two probability scales at one `auto_merge` threshold. S8 never says whether integration tests train or load — and EM on `base_10`'s 23 records is degenerate either way.
**THE FIX:** Add a `training:` block to S6 that Pydantic rejects if incomplete: `{deterministic_rules: [str], recall: float, u_max_pairs: int, u_seed: int (required, no default), em_blocking_rules: [str] (min 2), em: {fix_u_probabilities: true}}`, and persist all of it verbatim into `model_registry.metrics`. Rewrite S4.3's train bullet as an ordered call sequence with the Splink 4 namespaced names (`linker.training.*`, `linker.inference.predict`, `linker.clustering.cluster_pairwise_predictions_at_threshold`). Store the model at `s3://<bucket>/models/{tenant}/model_v{N}.json`; make `model_registry.params_path` that URI; write object first, registry row second; allocate `model_version` as zero-padded `max+1` inside the registry insert transaction; add `status ENUM{active, superseded}` and state "`er match` loads the single `status='active'` row unless `--model-version` overrides." Define `corpus_snapshot` as the DuckLake snapshot version the model was trained against. ## DECISIONS THE USER MUST MAKE

**1. Incremental scoring mechanism.**
*Options:* (a) Splink owns blocking — two passes (`find_matches_to_new_records` for new-vs-corpus + a batch-only `dedupe_only` Linker for new-vs-new), `int_blocking_keys` demoted to rule-generation source, parity artifact and benchmark metric. (b) The dbt candidate table is authoritative, scored via Splink's *internal* entry points (`compute_comparison_vector_values_from_id_pairs_sqls`, `predict_from_comparison_vectors_sqls_using_settings`).
*Recommendation:* **(a).** (b) pins you to unsupported internals that already moved in the 5.0 line, for a candidate set Splink recomputes anyway. Cost of (a): you must accept that incremental candidate generation is Splink's, and that `int_blocking_keys` earns its keep as the parity oracle (T-BLK-1) and the touched-subgraph driver.

**2. `entity_membership` representation.**
*Options:* (a) Current state — one row per record, `MERGE INTO`, all history in `entity_events`. (b) Append-only bitemporal with `valid_from`/`valid_to`/`is_current`.
*Recommendation:* **(a).** S4.5's affected-subgraph join and `member_removed` both assume current state; `entity_events` already exists as the log and S3 already promises replay. (b) costs a window function on every read for history that is already recorded elsewhere.

**3. Term-frequency policy.**
*Options:* (a) Freeze TF at training time, persisted as `tf_lookup` keyed by `tf_snapshot_id`, registered before every scoring call, refreshed only by the full pass. (b) Recompute TF per batch from the current corpus.
*Recommendation:* **(a).** (b) makes `match_scores` non-reproducible, adds a full-corpus aggregation to every incremental run (destroying the S10.3 headline ratio), and lets pairs cross `auto_merge` with no new evidence. (a)'s cost is a bounded, measurable drift from a from-scratch run — quantify it with T-TF-1 rather than asserting it away.

**4. `never_match` semantics.**
*Options:* (a) Edge-level only — remove the edge, detect co-clustered violations post-hoc, write a `violated_assertion` row to `review_queue`, restate T-ASSERT-1 accordingly. (b) Partition-level — after clustering, cut the minimum-probability edge on the shortest `a–b` path, log the cut in `entity_events`, re-run components to a bounded fixpoint, escalate to review when every path is at or above `auto_merge`.
*Recommendation:* **(a) for v1, with the invariant stated honestly, plus CONTRADICTION-1 as a hard pre-clustering failure.** (b) is the semantics a steward expects and should be scheduled, but it is a constrained-clustering problem with its own convergence proof; shipping (a) silently — which is the current state — is the only unacceptable option.

**5. Record identity.**
*Options:* (a) Derived scalar `record_key = source_system || ':' || source_record_id`, materialized on `std_records`, used as Splink's `unique_id_column_name`. (b) Native composite — `unique_id_column_name='source_record_id'`, `source_dataset_column_name='source_system'`, which Splink supports and `raw_records` already makes unique-within-dataset.
*Recommendation:* **(a).** (b) is legitimate and avoids a derived column, but it forces two-column joins through `match_scores`, `assertions`, `review_queue`, the blocking key table and the label-propagation SQL, and it makes the canonical-ordering invariant a lexicographic tuple comparison in every writer. One scalar plus a `':'`-forbidden test is cheaper everywhere it is used.

**6. `raw_records` semantics.**
*Options:* (a) Append-only version history (`content_hash` in the logical key); `std_records` carries `content_hash` and selects the greatest `ingested_at` per record. (b) Current-state upsert on `(source_system, source_record_id)` via `MERGE INTO`, with history discarded.
*Recommendation:* **(a).** It matches S4.1's "Appends", preserves the audit trail T-SNAP-1 trades on, and costs one column on `std_records` plus one uniqueness test. Whichever is chosen, S3's `landing.py # raw_records upsert` and S4.1's "Appends to `raw_records`" must stop disagreeing.
