## Description

Commit the M2-stageable half of `base_10`'s expected set in the S8.2.1 format: `std_hashes.csv` (asserted now, by T-STD-1's committed-file arm), plus `membership.csv` and `events.csv`, which S12 says are authored in M2 and first asserted in M3. All three follow the S8.2.1 encoding rules — literal headers, the `\N` null token, byte-wise ascending sort on the full column tuple, no `VOLATILE_COLUMNS` — and use symbolic `entity_label`s allocated in ascending order of the minimum `record_key` in each group, never ULIDs. The integration arm asserts the standardized corpus against the committed `std_hashes.csv`, which is the first end-to-end use of a committed expectation.

## Scope

### In scope

- `expected/base/std_hashes.csv`: 23 rows, header `source_system,source_record_id,std_hash`, generated from a real standardize run and committed
- `expected/base/membership.csv`: header `persona_id,source_system,source_record_id,entity_label`, groups equal to `truth.csv`'s personas, labels `E1..E10` by the S8.2.1 allocation rule
- `expected/base/events.csv`: header `entity_label,event_type,count` — the base-phase-from-empty-lake expectation
- A fixture-lint unit test covering headers, sort order, null token, label space and volatile-column absence
- `tests/integration/scenarios/test_base_10_std.py`: ingest + standardize `base_10`, compare the computed `(source_system, source_record_id, std_hash)` set to the committed file

### Out of scope

- `expected/base/golden.csv` and `lineage.csv` (ER-090, M4)
- Asserting `membership.csv` or `events.csv` against a live run — `entity_membership` and `entity_events` are not populated until M3 (ER-074 and the scenario tickets that consume this file)
- Any `batch/`, `refresh/` or `resurrect/` phase directory
- Regenerating or editing the input CSVs or the hashing function to make a comparison pass

## Design decisions applied

Closes M7 (expected files must be authorable and ID-insensitive) and the MINOR milestone-ordering finding (stage `base_10`'s expected set: std hashes + membership crosswalk in M2, golden in M4). Easy to miss: `entity_label` allocation is by ascending minimum `record_key` **of the expected group**, and the loader re-derives it at compare time — a hand-assigned or ULID label breaks every later scenario; every expected file is stored sorted, and a mis-sorted committed file must fail the unit lint, never the scenario test; nulls are the two-character `\N`, an empty field is the distinct empty-string value; `std_hashes.csv` is regenerated by re-running the pipeline, never hand-edited, and a diff to it is a deliberate act.

## Acceptance criteria

- [ ] AC1: `std_hashes.csv` has the literal header `source_system,source_record_id,std_hash`, exactly 23 data rows, every `std_hash` matching `^[0-9a-f]{64}$`, and no `\N` token.
- [ ] AC2: After ingesting and standardizing `base_10` on a fresh namespace, the set of `(source_system, source_record_id, table_content_hash(row))` computed from `int_std_records` equals the committed `std_hashes.csv` exactly, in both directions, with the symmetric difference printed on failure.
- [ ] AC3: `membership.csv` has the literal S8.2.1 header, 23 rows, an `entity_label` domain of exactly `{E1,…,E10}`, and its grouping of `(source_system, source_record_id)` is set-equal to `truth.csv`'s persona grouping with sizes `[4,3,3,2,2,2,2,2,2,1]`.
- [ ] AC4: Re-deriving the label assignment from `membership.csv` by the S8.2.1 rule — labels ordered by ascending minimum `record_key` of each group — reproduces the committed labels exactly, and no field in the file matches a ULID pattern.
- [ ] AC5: `events.csv` has the literal header `entity_label,event_type,count` and contains exactly one `created` row with `count=1` per label and no other `event_type`, consistent with a base phase run against an empty lake.
- [ ] AC6: Every committed expected file is byte-wise ascending-sorted on the UTF-8 encoding of its full column tuple in header order, and no header field name is a member of `VOLATILE_COLUMNS` (the unit test fails on a deliberately shuffled copy).
