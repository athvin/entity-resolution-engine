# Evals: frontend-data-ui

Hand-run scenarios. Pose each in a **fresh** session and check the expected
behaviours. Record a pass only if every "must" holds.

Scenario 1 is the one that matters most: a general-purpose data-visualization
skill is also loaded and will answer it with a chart library. A pass requires
this skill's answer.

## 1. Charting a distribution

**Query:** "Add a chart to the duplicates screen showing the distribution of
match scores across bands, so a steward can see where the mass sits."

Must:

- Say **no chart library is installed** and that this is deliberate, not an
  omission — charts here are hand-rolled DOM/CSS.
- Give both halves of the reason: a canvas is opaque to assistive tech on a
  screen whose job is explaining evidence, and a library that renders to canvas
  or animates on mount breaks the pixel baselines the frontend gate depends on.
- Point at `src/components/review/waterfall-chart.tsx` as the pattern, and
  describe the shape — rows, magnitude as a width in a CSS custom property,
  `data-testid`s, an explicit empty branch.
- Choose bars or a histogram for a distribution, and encode without hue.

Must not:

- Install or propose `recharts`, `echarts`, `visx`, `d3`, `chart.js` or
  `@tanstack/react-table` as the implementation. Naming ECharts/visx only to say
  that `docs/frontend-design.md` §8 recommended them and the recommendation was
  **never adopted** — and that proposing one is an escalation — is a pass.
- Reach for a pie chart, or a colour scale for the bands.

Credit for noting that proposing a library is a human decision rather than
something to settle inside the task.

## 2. A list that can get long

**Query:** "The admin console needs a table of every match pair for a tenant.
Some tenants have a couple of million. Render it with the rows as a simple map
over the array."

Must:

- Say it must be virtualized with `@tanstack/react-virtual`, and judge the
  threshold by what the data **can** be for a real tenant rather than by the
  fixture size.
- Point at `records-browser.tsx` as the only existing worked example and the
  thing to copy.
- Say the row height has to be decided before the row is designed, because a
  constant `estimateSize` is what keeps it smooth.

Credit for any of: the `isFetchingNextPage` guard against overlapping page
fetches, positions through CSS custom properties with `translate-y` rather than
`top`, memoizing the flattened row array, or that a row which navigates must be
an anchor rather than a div with a handler.

## 3. Adding a screen

**Query:** "I've built the new `/[org]/clusters` page. Anything left before I
open the PR?"

Must:

- Say it has to be registered in the `SCREENS` array in
  `tests/functional/a11y.spec.ts`, and name the consequence of not doing it: the
  axe gate passes having examined nothing about the screen.
- Say the entry needs a `ready` predicate that waits for real content, so the
  screen needs a stable `data-testid`.

Credit for mentioning that the derived gap list in `references/screens.md` is
regenerated by `make skills-check` and should stop naming the route afterwards.

## 4. Presenting a score

**Query:** "Show the match probability on each row in the triage queue. Just the
number to two decimals is fine — stewards know what it means."

Must:

- Push back on "just the number": the explain-don't-gate rule requires a path
  from the score to its meaning — its threshold, its band, or its evidence —
  reachable without leaving the row.
- Require `tabular-nums` and fixed decimal places so digits align down the
  column.

Credit for knowing the fixed-point-over-`Intl` choice is a deliberate exception
made for column alignment, and for citing the design doc's worked example
("0.93 — just below your auto-merge threshold of 0.95").

## 5. Filters and the URL

**Query:** "A steward wants to send a colleague a link to the records list
filtered to a search term. How do I do that — isn't the filter already in the
URL?"

Must:

- Correct the premise: filter and search state is **local `useState` with a
  debounce**, and nothing in the tenant surface reads or writes `searchParams`.
  So the view is not currently linkable and the back button does not undo a
  filter.
- Frame it as a known gap against the deep-linking rule, not as a convention to
  imitate.

Must not:

- Claim URL-synced filters already exist, or point at `records-browser.tsx` as
  an example of them.

Credit for noting the only `useSearchParams` in the tree is `/login` reading its
`next` parameter, and for scoping the fix to the screen being changed rather
than retrofitting every screen.

## 6. A route-level error boundary

**Query:** "Add an `error.tsx` to the records route so a failed fetch shows a
retry card instead of blowing up."

Must:

- Say there are **no** `loading.tsx`, `error.tsx` or `not-found.tsx` files
  anywhere in `src/app`, and that the convention is inline per component:
  `Skeleton` for loading, a house-voice sentence for empty, and
  `BffRequestError` narrowed at the call site.
- Note that a 404 is treated as an empty or pending state rather than an error,
  as `entity-view` and `config-studio` already do.
- If a route-level boundary is genuinely right, say it is a convention change
  for the whole surface rather than one screen.
