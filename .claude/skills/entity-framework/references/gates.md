## The entity lint pass (the V-rules)

**Command:** `cd rust && cargo run -q -p er-entity-cli -- lint --root ..`
**Runs in:** first, inside `verify` — and it short-circuits, because every later
pass assumes a conforming catalog.

The conventions an `entity.yaml` must hold. They live in
`rust/crates/er-entity-lint` as a registry of rule values, so the reference is
generated rather than maintained:

- **[`docs/entity-lint-rules.md`](../../../../docs/entity-lint-rules.md)** — every
  rule with its reasoning and a conforming/violating example pair. Generated by
  `er-entity lint --docs` and byte-compared by `verify`, so it cannot drift.
- `er-entity lint --list` — the same table at the terminal.
- `er-entity lint --explain V4` — one rule in full. **Reach for this first when a
  V-code fires**; the prose says why the rule exists, not just what it checks.

Two things to know when a finding appears:

- **Severity matters.** Error-severity findings fail the gate and block
  generation. `Severity::Warning` findings print and do not fail — V15 (tenant
  scope is indexed) is the current warning, and
  `er-entity-lint/tests/tree_is_clean.rs` pins exactly which entities carry that
  debt, so adding a new one fails the test.
- **The pass reports everything at once**, unlike the old fail-fast validator.
  A new entity converges in one run; expect several codes from one mistake (a
  missing `id` reports both V1 and V2, since the key can no longer name it).

**Adding a rule** is one file in `er-entity-lint/src/rules/`, one line in the
registry (`src/rules/mod.rs`), and one fixture directory under
`er-entity-lint/tests/fixtures/<CODE>_<case>/` holding a minimal `entity.yaml`
plus `expected.txt`. `UPDATE_EXPECT=1 cargo test -p er-entity-lint` writes the
expectation from current behaviour — read the diff, because that file *is* the
assertion. Two tests enforce the discipline: every rule must have a fixture, and
every rule must carry title, reasoning and both examples. Codes are append-only.

## The verify gate (staleness + orphans + analyser)

**Command:** `cd rust && cargo run -q -p er-entity-cli -- verify --root ..`
**Runs in:** CI's `lint` job (`.github/workflows/rust.yml`), `make check`
(target `entities-check`).

Four checks in one:
0. **Entity lint** — the V-rules above, run first and short-circuiting.
1. **Staleness** — regenerates the whole tree in memory and byte-compares every
   generated file (incl. `docs/erd.md` and `docs/entity-lint-rules.md`). Failure:
   `er-entity check: N generated file(s) are stale or missing` → run gen and
   commit the diff.
2. **Orphans** — any file in a generated directory that gen did not emit.
   Failure names the files → delete them (a removed entity/statement leaves
   its output behind; gen never deletes).
3. **Analyse** — loads every statement, plans full-mode ones via DataFusion,
   runs the E0xx passes. Failure: `[E0xx] path: message` → the remedy table in
   `statements.md`, beside this one and reached from the skill body.

## The oracle

**Test:** `er-sql-check/tests/oracle.rs::oracle_lake_reads_match_their_declared_shape`
(plain `cargo test -p er-sql-check`).

For every lake read statement it asks a real DuckDB `DESCRIBE <statement>`
(each `$param` substituted with a typed NULL literal; the snapshot pin stripped)
and compares name+type against the declaration. It catches
DuckDB-vs-DataFusion divergence the analyser cannot — classically
`sum(BIGINT)` → HUGEINT. Fix: `CAST` in the SQL or correct the declared type.
This is the only shape check a `mode: partial` read gets.

## The posterity gates (static)

**`er-schema/tests/declared_names.rs::every_lake_main_literal_names_a_declared_relation`**
— any `lake.main.<name>` literal anywhere in the workspace must name a relation
the S5 registry (or an entity) declares. Fix: declare the relation first;
inline DDL cannot ship. (`dedupe-cli` is exempt: operator-named outputs.)

**`er-schema/tests/freeform_sql.rs`** — two scans:
- `query_strings_has_no_callers_outside_the_engine_core` — product code never
  calls `Session::query_strings`. A session-temp scratch read uses the visibly
  exempt `Session::query_scratch_strings`; everything persistent is a declared
  statement.
- `er_server_builds_no_lake_sql` — `er-server/src` names no `lake.main.<x>` at
  all; its lake access is generated statements plus the er-golden merge-plan
  generator. Fix: declare a statement, never assemble SQL in er-server.

**`er-schema/tests/model_registry.rs`** + `model_registry_golden.json` — the
registry is byte-pinned. A registry change must update the golden
(`json.dumps(data, indent=1, ensure_ascii=False) + '\n'`, byte-exact).

## The posterity gates (live)

**`er-cli/tests/lake_e2e.rs::the_lake_contains_only_declared_relations`**
(needs `DEDUPE_E2E_DUCKLAKE=1`) — after a full pipeline run, the live lake
holds only declared relations. Catches dynamically-built names the static scan
cannot see.

**`er-server/tests/pg_schema_coverage.rs::public_schema_contains_only_declared_tables`**
(needs `ER_TEST_PG_DSN`) — after boot provisioning, `public.*` holds only the
tables the generated `POSTGRES_BASELINE` declares.

**`er-entity-gen/tests/registry_matches_entities.rs`** — the entity catalog and
the HAND-MAINTAINED S5 registry (`er_schema::model::all_specs()`) must render
the same `create_table_sql` for every DDL-owned lake relation they both
describe.

There are **two schema sources**, and the one that runs at runtime is the
registry: `er_cli::create_ddl_table` builds every lake table from `all_specs()`,
not from the entity-generated DDL. So **a lake column change belongs in both** —
`entities/<e>/entity.yaml` *and* `crates/er-schema/src/model.rs`, plus that
crate's golden dump. An entity-only change regenerates cleanly, passes
`er-entity verify` and `er-entity-diff`, and then fails inside a run with
`Binder Error: Referenced column "…" not found`, because the table was created
from a registry that never heard of the column. That is exactly how E9b found
it.

`er-entity-diff` cannot catch this by construction: it compares the catalog
against a **live** store, so with no live column there is nothing to diff. The
golden in `er-schema` is hand-maintained at `indent=1` — check round-trip
fidelity before editing it, or a four-column change reformats 4,200 lines.

**The reconciler's contract** — `er-entity-diff/tests/pg_reconcile.rs` (needs
`ER_TEST_PG_DSN`), `er-entity-diff/tests/lake_reconcile.rs` (needs
`DEDUPE_E2E_DUCKLAKE=1`) and `er-server/tests/pg_migrate_tenants.rs` (needs
both): an empty store converges to the catalog and the ledger says so, a
second pass writes nothing, a dropped nullable column comes back as an
`applied` row, an extra live column is reported as ahead and left alone, a
retyped column is refused with nothing written, a stage-materialised lake
relation is never touched, and the deploy sweep reports `migrated`, `current`
and `breaking` per tenant with a breaking lake failing every job for that
tenant before a stage runs. A reconciler change that breaks any of these is a
production schema bug, not a test to update.

**The DuckLake e2e tiers** (`DEDUPE_E2E_DUCKLAKE=1 DEDUPE_E2E_EXTENSIONS=1`,
`make check-e2e`) — the base_10 committed goldens must stay byte-identical;
this is the determinism proof every framework change rides on.

## The generator plan-vector tests

In `rust/crates/er-sql-check/src/stage.rs` (`cargo test -p er-sql-check`):
the golden-record and lineage mart assembly (person + account), the
standardize stg/int_std SQL (person + account), and the merge-plan generator
(every policy × protect × since = 20 vectors). A generator change that emits an
un-plannable shape fails here, not at runtime. New config-driven SQL must add
its vectors alongside these. (If planning needs a new DuckDB function stub,
that lives in the pinned `ff-analysis` — bump requires a feather-flow tag.)

## Running everything locally

```bash
make check          # fmt + clippy + er-entity verify + workspace tests
cd rust && DEDUPE_E2E_DUCKLAKE=1 DEDUPE_E2E_EXTENSIONS=1 \
  cargo test -q -p er-cli --test lake_e2e   # the determinism tier
```

Postgres-gated suites expect a disposable DB, e.g.
`docker run -d --rm --name er-pg-test -e POSTGRES_USER=er -e POSTGRES_PASSWORD=er \
 -e POSTGRES_DB=er -p 5455:5432 postgres:16-alpine` then
`ER_TEST_PG_DSN='host=localhost port=5455 user=er password=er dbname=er'`.
Tear the container down afterwards.
